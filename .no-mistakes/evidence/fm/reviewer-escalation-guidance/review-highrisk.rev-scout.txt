# Review: `change.diff` → `auth.py` `can_access`

**TL;DR: rethink.** The change does touch only one function, but it breaks authorization. The new code caches the access result under the account id alone. Whichever user checks an account first decides the answer for every later user. If that first user had access, everyone gets access. If they didn't, legitimate users are denied. The change also removes the tenant check outright, while the comment only says moving it to the gateway is "planned". This is a high-risk auth change, so I recommend a senior security reviewer before it goes any further.

## Findings

1. **Material: shared cache causes privilege escalation across users.** `auth.py:5-7`. `CACHE` is a module-level dict keyed only by `account.id`. The stored value is computed from `user.account_ids` for whoever calls first, then returned to every later caller whatever their identity. Example: user A owns account 42 and calls first, so `CACHE[42] = True`. User B, who has no rights to account 42, then gets `True`. This is a direct authorization bypass.
2. **Material: the reverse case denies access wrongly.** Same lines. If an unauthorized user checks first, `False` is cached and every authorized user is locked out until the process restarts.
3. **Material: the tenant isolation check is gone.** `change.diff:5` removes `user.tenant_id == account.tenant_id`. The comment at `auth.py:4` says ownership checking moves to the gateway "(planned)". Nothing in the reviewed files shows a gateway check exists yet, so for now the code has no tenant boundary.
4. **Material: the cache never refreshes.** `auth.py:1,5-6`. Entries never expire and are never invalidated, so revoking or granting access has no effect until a restart. The dict also grows with every account id it sees (minor on its own).
5. **Minor: no locking around the cache.** `auth.py:5-6` checks and then sets with no lock. Under the GIL this can't corrupt the dict, but two threads can race to write the first value. That doesn't matter much given finding 1.
6. **Minor: the diff doesn't match the file.** `CACHE = {}` sits at `auth.py:1`, but the diff never adds it. Either it existed before the change or the diff is incomplete. The hunk header `@@` (`change.diff:3`) also has no line ranges, so the diff can't be applied mechanically.

## Unprompted observations

- The comment at `auth.py:4` presents the cache as a deliberate design ("cached globally"). This doesn't look like a typo. It reads as a misunderstanding of what the cache key has to include. A correct cache would be keyed on at least `(user.id, account.id)` and would include the tenant check.
- The new code doesn't use `user.tenant_id` or `account.tenant_id` at all. If the "gateway (planned)" work never lands, nothing will flag that the check is missing.
- There are no tests in the tree, so nothing would catch any of the above.

## Escalation

This is a high-risk authorization change. I recommend a senior or security reviewer, plus a second pass by whoever owns the gateway, to confirm whether any tenant check exists outside this file.

## Verdict: **rethink**

**Single highest-leverage change:** revert `can_access` to the original check that verifies both tenant and account. If caching is really needed, key it per user (`(user.id, account.id)` at minimum), give it invalidation, and keep the tenant check until the gateway is shown to enforce it.
